# P7.4 Real Codex Release Acceptance

This is a human gate. CI fixtures and local Core tests do not prove that the
installed Codex client invokes the published Plugin hooks correctly.

## Environment record

Record these values without recording prompts, tokens, absolute user paths, or
SQLite contents:

```text
Codex client/version:
OS/version:
Python major/minor:
Plugin version:
Bundle hash:
Test date:
Tester:
```

## Acceptance sequence

1. Install the release marketplace or extracted release bundle in a clean
   Codex profile.
2. Run `$skilltree-bootstrap install --python "<absolute-python-path>"`.
3. Confirm `skilltree doctor --json` reports the Plugin/Core/Schema and venv
   checks as pass.
4. Confirm a normal prompt remains fail-open when consent is disabled.
5. Enable only the documented consent switches and run one read-only route.
6. Confirm `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, and `Stop` Hook
   behavior using a harmless fixture; verify stdout is valid Codex Hook JSON.
7. Restart Codex and repeat the doctor check to verify persistence.
8. Install the next release over the existing data directory and verify the
   prior runtime remains recoverable if upgrade fails.
9. Record pass/fail evidence and the exact bundle hash. Do not attach raw Hook
   payloads, prompts, credentials, or local database files.

## Required evidence

The gate is `passed` only when every step has a timestamped, redacted result,
the installed bundle hash matches the signed asset, and no unexpected Hook
stdout or runtime error is observed. Otherwise record `blocked` or `failed`;
do not convert fixture success into a real-Codex claim.
